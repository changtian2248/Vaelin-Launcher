## Q2：底座选 A（复用上游 GPL 组件）+ 项目整体 GPL-3.0，在第 6 条约束下成立吗？

**判定：有条件成立——GPL 代价本身自洽，但"参考 vs 依赖"的冲突必须先由用户裁决，且 02 文档的论证顺序有倾向性。**

分层说：

1. **GPL-3.0 代价内部自洽，这部分成立**。证据链：规格书 379 行 AI 生成模块强制 `license: GPL-3.0`（6.2 节），模块模板强制 GPL（02:74 引用）——模块生态已是 GPL 世界，宿主整体 GPL-3.0 与之匹配，链接 GPL-3.0 的 Pojav 系 runtime 合规（research §6:117-119 已读三家 LICENSE 均 GPL-3.0）。
2. **但规格书文本不支持 lead 的 reinterpretation**。规格书第 5 行写明参考项目"**仅作参考**……不 Fork 他人仓库、不以他人 APK 为基底"，且点名列表包含"Pojav 系启动器、FCL、ZL2"。02 选项 A 是"直接依赖 PojavLauncher/FoldCraftLauncher/ZalithLauncher2 的 runtime 组件"（02:72）——**链接使用不是参考**，这与第 5 行字面直接冲突。lead 在 02:75 说"第 6 条要防的是换皮，不是禁止使用开源库"，并拿规格书自己引用 cubiomes 作类比——但 cubiomes/schematic4j/Nucleation 是规格书**点名允许**引入的（第 5 行明确"源码引入"），Pojav 系 runtime 不在点名允许之列。类比不成立。
3. **lead 的处置流程是对的，叙述顺序不对**。02:88 确实把 A/B/C 列为"待用户裁决"，02 §9 第 1、2 条也挂了裁决项。但 02:74-77 先替选项 A 写完合规辩护，再请裁决——裁决项在文案上已被预设答案。正确写法是把"第 5 行'仅作参考'是否允许链接依赖"作为独立裁决问题原文呈报，不带辩护。
4. **替代路径**（若用户拒绝整体 GPL 或拒绝链接上游）：
   - B 自研：02:80-81 已判首版不可达，我同意。
   - **运行时独立 APK + 进程隔离**：把 GPL runtime 做成独立安装的应用，Vaelin 主 APK 不链接，经 IPC 调用（GPL 的 aggregate 概念下弱化 combined work 争议）。**但要如实标注**：MC 的渲染/输入是单进程内紧密循环，Android 上跨进程跑游戏渲染基本不可行（未验证，属强怀疑），此路径技术上大概率死路，列出仅为完整性。
   - 结论：A 是唯一现实路径，但它的合法性系于用户对第 5 行的裁决，不是 lead 可以技术裁决的。

## Q3：research 三条风险在 02 中的覆盖情况

### R1 Terracotta AGPL-3.0（research §7:144-159）——**02 未覆盖，风险与解法都没写**

02 §6.3 许可清单（02:184-188）只列了 cubiomes/schematic4j/Nucleation/Pojav 系，**通篇没有 Terracotta 与 EasyTier**。规格书 32 条要求"陶瓦/EasyTier 联机"，lead 把 AGPL 风险完全漏在方案外。补充判定：AGPL-3.0 的网络条款（§13）主要约束网络服务场景，但**分发链接了 AGPL 库的 APK 会使整体受 AGPL 约束**（比 GPL-3.0 更强）。可执行应对（02 未给）：① 优先 EasyTier 路线（LGPL-3.0，链接合规，且 research §7:150 明确"非 AGPL"）；② Terracotta 只读代码学协议、自行实现（"参考"不触发 copyleft）；③ 若必须用 Terracotta-lib，把它做成**独立 AGPL 模块 APK** 经服务注册表交互——模块体系恰好为此而生，但模块与宿主的动态加载边界是否阻断 copyleft 传染属法律灰区（标注：不是法律结论）。注意 EasyTier 下载状态：03:156 仍"⏳ 下载中"，LGPL 合规路径的源码还没到手。

### R2 Android 14 targetSdk≥34 禁止对动态加载 dex 持可写权限（research §2:38）——**02 未覆盖，这是模块系统的硬约束**

02 §4.2 加载链路（02:104-110）从"读索引 DB"到"反射实例化"没有一步处理 dex 文件权限；02:108 的 `DexClassLoader(dex, optimizedDir=私有目录...)` 在 targetSdk≥34 时，若模块 dex 从 zip 解压后保持可写即**直接加载失败**。02 §4.4 只处理了 native 库的 SELinux 问题（02:122-129），dex 的对应问题漏了。可执行应对：安装期解压完成后立即对 dex 置只读并校验，加载前复查；升级/卸载流程才恢复写权限；"清 dexopt 缓存"（开发者选项 D 区，规格书 335 行）要区分系统管理的 odex（允许清理）与 dex 源文件（不可写）。**这条必须进 P0**，否则模块加载链路第一次真机验证就爆。

### R3 模块 APK 共享宿主 Compose runtime 无可核实先例（research §2:44-46）——**02 把它当可行前提，未安排验证**

research 明确"未找到可核实的公开先例……Composable 编译器产出的调用链对库版本敏感……建议最小工程实测"（research §2:45-46）。02 §4.2（02:111）的类空间规则直接以"parent=宿主 classloader 保证模块能用 Compose 运行时"为前提，全程无 spike 安排；01 §5.4 未验证清单（01:194-206）也没有这条。**这是 01/02 双双未接住 research 唯一一条"最大不确定性"定级的风险**。可执行应对：P0 阶段一个最小 spike——宿主打一个仅含 `@Composable` 函数的最小模块 dex，跨 Compose BOM 小版本加载验证。若 spike 失败，整个模块 UI 设计要改（模块自带 Compose 副本 → 5MB dex 红线与多副本冲突），越早知道越好。

## Q4：版本矩阵 AGP 9.5.0 + Gradle 9.8.2 + Kotlin 2.4.21 + Compose BOM 2026.09.00

**判定：中高风险，其中两个维度同时超出 KGP 官方兼容表；必须 P0 第一天用 assembleDebug 关闭，lead 的回退组选得过深。**

- 事实核对：AGP 9.5.0 要求 Gradle ≥9.6.0（research §1:17，官方兼容表），Gradle 9.8.2 满足——**这一维没问题**。KGP 2.4.21 官方兼容表上限 AGP 9.3.1 / Gradle 9.7.0（research §1:23）——**AGP 与 Gradle 两个维度同时超表**。03 文档自己标了"待验证"（03:66、03:178），这个自觉是对的。
- 风险等级判"中高"而非"高"的理由：KGP 对超表的高版本 AGP/Gradle 实践中多数可跑（有警告），且 AGP 9.x 有"内置 Kotlin"路线（research §1:22，要求 KGP 2.2.10+）可绕开独立 KGP 兼容性。判"中高"而非"低"的理由：一旦踩坑，排查面横跨 AGP/KGP/Gradle 三方 release notes，且 Compose 编译器插件与 Kotlin 版本强绑定（research §1:26），配置路径因"内置 vs 独立 KGP"而不同，试错成本高。
- **回退组裁决：lead 的回退（AGP 8.13.2 + Gradle 8.x，03:66）过深，不采纳**。更近的回退点：**AGP 9.3.1 + Gradle 9.7.0 + KGP 2.4.21**——三者全部落在 KGP 2.4.21 官方兼容表内（research §1:23），Compose BOM 与 AGP 无直接耦合、与 Kotlin 2.x 编译器兼容，无需降到 8.x 线。第二回退（若 9.3.1 仍有问题）才是 AGP 内置 Kotlin 路线或 8.x。顺序：先 9.5.0 实测 → 回退 9.3.1/9.7.0 → 内置 Kotlin → 8.x。
- 附带指出：03:55 的"latest 为 9.6.0-alpha02"推理正确（maven-metadata 的 latest 含预发布，9.5.0 是稳定线最新），这点站得住。

## Q5：其他"看起来完成、实际会爆炸"的缺口（只列我确信的）

1. **地区闸的 READ_PHONE_STATE 权限流程完全没设计**。research §8:167-168 实锤：`getSimCountryIso`/`getNetworkCountryIso` 需要 `READ_PHONE_STATE` 运行时权限。02 §6.1（02:174-178）只写了"双信号 + 双失败默认大陆"，没写：谁在什么时机请求权限、用户拒绝算不算"信号失败"（拒绝→默认大陆在合规上保守，但启动器一上来要电话权限的体验与上架审核问题没人管过）。这是地区闸（已锁条目 8/25）落地的第一道坎，三份文档全部沉默。

2. **模块 Compose 编译器版本与宿主 runtime 的耦合没有治理机制**。规格书 23 条 CI 只查"无 androidx/compose/ 类 + apiVersion 匹配"，但 apiVersion 是 lab-api 的版本，**不覆盖 Compose 编译器协议版本**。宿主升级 Compose BOM 后，用旧编译器构建的已发布模块可能直接崩（这正是 R3 无先例的深层原因）。module.json 需要增加 Compose 编译器/kotlinx metadata 级别的兼容性声明，或 apiVersion 语义显式绑定 BOM 版本。01/02 均未提。这是模块生态上线后必然爆炸、上线前可低成本预防的典型。

3. **51 条首版范围与 P2/P5 排期的隐性矛盾**。规格书 34 条"游戏内只读查看器"是种子地图功能的一部分（58 行），而 51 条说种子地图完成即首版发布。02 §8（02:208-218）把世界工具排 P2、游戏内能力（含查看器依赖的底座）排 P4-P5——意味着首版种子地图**必然不含**游戏内查看器，这是对 34 条的范围裁剪，02 没有显式声明，验收时会对不上 34 条的原文。需要一句话拍板："首版种子地图不含游戏内查看器，查看器随 P5 补"。

4. **选 A 的物质前提还悬着**：03:153-159 显示 Pojav/FCL/Zalith/EasyTier 四仓库全部"⏳ 下载中"、Nucleation"未定位"；03:167-169 实测 gh-proxy 仅 40-107 KB/s。底座选 A 依赖拿到上游 runtime 源码，而大仓库经此代理可能数小时且易断；gh-proxy 对 git clone 的支持从未验证（01:204 已列，但选 A 的紧迫性没传导到这个验证上）。02:72 的方案把"能拿到组件"当成既成事实。**在四仓库落盘前，Q2 的裁决是纸面裁决**。

5. **02:160 引用了拿不到的数据**：§5.2 内存纪律"palette 上限（Axolotl 的实测阈值可作起点）"——但 Axolotl 参考实现的来源在 03 §6 清单中根本没有（不在下载列表，也不在 research §6 表格里）。这个阈值目前无处可抄，要么补 Axolotl 到 sources 下载清单，要么删掉这个引用改为自行定阈值。小问题，但它是"看起来有依据、实际是空的"的样本。
