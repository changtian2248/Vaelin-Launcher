## 二、可实现性三分类清单

判定基准：本机 Windows 原生构建、JDK21 + 待装 Android SDK/NDK/Gradle、arm64-v8a 单 ABI、GitHub 经 gh-proxy.com 镜像可达。注意：**Windows 上交叉编译 arm64 Android native 库完全常规**（NDK 官方支持），此前"PRoot aarch64 无官方 NDK"的环境障碍已被用户决策（§2 第 9 条记忆：Windows 原生构建）解除，仅剩 CI 兜底仍成立。

## 三、规格书问题清单（矛盾 / 不可行 / 含糊）

**P-1【含糊·无法单独验收】条目 3（核心价值主张）**："玩起来之后体验最强"是最强级比较级断言，没有比较对象与度量标准，不可验收。建议降级为愿景陈述，不进验收矩阵。

**P-2【结构性缺口·最重要的发现】缺少"MC Java 启动底座"条目**：规格书通篇假设启动器能启动 Minecraft Java 版（32 联机、31 悬浮、42 C/L 区、34 游戏内查看器都建立在"游戏已能跑"之上），但 59 条中**没有任何一条**定义：JRE 运行时来源与许可（哪个 JRE 发行版、arm64 Linux Android 端 JRE——PoJav 系用的是自构建的 JRE 8/17/21 移植）、渲染器栈（Zink/VirGL/HGL 在 456 行被提及但无任何规格）、游戏进程启动方式（PRot 虚拟环境还是 Dalvik 直接挂 JVM——MC Java 版在 Android 上必须经 Linux 用户态兼容层或移植 JVM，这是整个项目**最大的单点技术风险**，其难度远超其余全部条目之和，而它被当成了既成事实）。参考项目（Pojav/FCL/ZL2）正是这个底座的提供者，但规格书只允许"参考不 Fork"——**从零重写这个底座在工程上等于重新实现 Pojav 核心数年工作量；不重写则违反第 6 条"从零构建"的字面语义**。这是规格书最大的内部张力，必须在需求确认阶段由用户裁决"启动底座"的实现边界（从零重写 / 复用上游开源组件并标注来源 / 以 GPL 合规方式链接）。按验收纪律，在底座条目缺位的情况下，51 条"种子地图完成即首版发布"是不可达的，因为种子地图的"游戏内只读查看器"依赖底座。

**P-3【含糊】条目 17/53 官方索引托管位置未指定**："官方索引（GitHub Release zip + 热更索引 JSON）"——JSON 托管在 GitHub raw/github.io 时，目标用户是国内玩家（条目 2），国内直连 GitHub 的可达性差，与"国内为主"的用户定位自相矛盾。需要镜像/CDN 策略（如 gh-proxy 类或对象存储）作为规格补充。

**P-4【潜在矛盾】条目 8 vs 条目 23/17**：条目 8 地区闸要求"下载……入口隐藏 + 动作拒绝"，条目 17/2.6 的模块安装路径含"索引下载（GitHub Release zip）"。模块索引下载**是否也受地区闸管辖**未明说：若管辖，大陆用户模块生态整体不可用（模块是产品心脏，自相矛盾）；若不管辖，闸的口径需要明确写清"地区闸只管游戏内容/整合包/资源三类分发，不管启动器自身功能分发"。建议显式补一行口径。

**P-5【含糊·验收不可行】条目 31"多渲染器兼容"**：兼容三个渲染器（Zink/VirGL/HGL）需要三种环境下实测，AI 侧无真机无 GPU；56 条已把多 ROM/渲染器验证划给用户侧，但"多渲染器兼容"作为 31 的验收标准时未标注"用户侧验收"。建议明确标注。

**P-6【条目内矛盾·轻微】条目 12 vs 149 行扩展点收缩**：条目 12 说模块能承载"UI 重构"，149 行 v1 明确不提供"往宿主既有页面任意塞 Composable"。v1 内"UI 重构"只能通过 THEME/HOME 等有限目标达成，字面上 12 是过承诺。建议在验收矩阵中把 12 的 v1 验收口径对齐 149 行。

**P-7【技术口径需复核】2.3 节 optimizedDir 与 native 兜底**：`os.chmod(0o755)` + `System.load` 兜底写法在 Android 10+ (targetSdk 29+) 上 `exec`/dlopen 非 app 私有目录 native 库受 W^X 限制（`untrusted_app` domain 只允许加载 data 目录中 app 自身的 lib），模块 native 库（cubiomes-bridge、Nucleation .so）若走"下载后动态 dlopen"路径，在 Android 10+ 上**大概率被 SELinux 拦截**；可行替代是 .so 打进模块 APK/zip 后放到 `nativeLibraryDir`（安装期即定）或使用 `ApplicationInfo.nativeLibraryDir` 注入 librarySearchPath。规格书这段兜底描述是老 ROM 时代的经验，对新系统不完全成立。需要实测关闭（未验证）。

**P-8【含糊】条目 28"逐字一致"**：渐变文字生成器"与参考实现逐字一致"——参考实现指哪个具体项目/哪个版本未指名；若无指定，验收时无法构造黄金样本。

**P-9【潜在版权/合规风险·规格未覆盖】条目 30"兼容 FCL 系格式"**：按特征解析他人私有格式（非公开 schema），属于格式逆向；规格书对这层的版权/许可口径未覆盖（参考项目许可未逐个核实，仅 schematic4j/Nucleation 标注"MIT 已核实"）。建议补"参考项目许可核实清单"为强制前置。

**P-10【条目 46 表述问题】"冷启动增加开销 < 10ms"**：这是**增量**指标（相对无模块系统的基线），不是绝对启动时间；验收时要先建立无模块基线的测量程序，规格未写明基线定义。

## 四、关键技术点独立判断

### 4.1 模块系统（DexClassLoader + 懒加载 + 崩溃隔离 + FeatureRegistry）
**总判：设计成熟度是全规格书最高的部分（102–221 行几乎是可直译成代码的规格），可实现，但有四个必须实测/注意的暗礁：**
1. **Recompose 异常传播**（L2）：如上二节所述，Compose ErrorBoundary 必须处理重组异常与协程异常两条路径，不能只靠 try-catch。这是 15 条最可能"写出来了但拦不住"的地方。
2. **DexClassLoader 的 parent 委派陷阱**：`parent = 宿主 classloader` 意味着模块类加载先查宿主——两个模块各自带同名工具类时会共享宿主可见版本或互相污染。规格书未写模块间类空间隔离策略。**建议**：parent 一律用宿主 Boot/SystemClassLoader 链，模块间经服务注册表接口寻址（2.8 已有此设计，恰好规避），但要禁止模块依赖"宿主 classloader 里恰好有的类"这个偶然性。
3. **W^X / SELinux**（P-7）：动态 dlopen 模块 native 库在 Android 10+ 的合规路径需要实测验证，不能照抄规格书 2.3 的兜底描述。
4. **apiVersion 次版本兼容的执行**：153 行"次版本只增能力不破坏"是纪律性声明，lab-api 编译期无机制强制；只能在 lab-api 维护规范层遵守，验收只能抽查。诚实标注：这是流程保障不是机制保障。

### 4.2 cubiomes 种子地图
**总判：技术路径全通，是三件套里确定性最高的。** C 库交叉编译无悬念；JNI 层指针生命周期用 `CriticalNative`/DirectByteBuffer 管理；瓦片地图 LRU32/并发2 是低风险参数。两个非技术注意点：① 结构映射表（34 条）初始数据编制是隐含工作量；② "与参考实现逐点一致"的验收样本要指定种子清单（建议 5–10 个覆盖不同 MC 版本与结构类型的已知种子），规格未列。

### 4.3 Nucleation 投影渲染（Rust→NDK）
**总判：这是世界工具三件套里唯一有"构建链难度"的点，判定为⚠️偏高。** 具体分解：
- cargo-ndk 交叉编译 aarch64-linux-android 在 Windows 上可用，但需要装 Rust + cargo-ndk + NDK 的 `rustup target add aarch64-linux-android`——本机 Rust **未装**（题设环境清单无 Rust），这是新增工具链依赖。
- Nucleation 是否提供稳定 C FFI 层规格书未写（"Rust→C FFI→NDK→JNI"为 424 行给出的链路，说明作者知道要做 FFI 桥）；若上游 FFI 不完整，需要自己写 Rust 侧 bridge crate——Rust 工程能力要求陡增。
- greedy meshing + 流式加载不 OOM：内存上限策略必须自设计（分块 + 顶点缓冲上限），无参考验收数值。
- 结论：可实现但应**排期上置于种子地图之后、作为第二优先级**（51 条里程碑也是这个顺序：种子地图先、投影热更后——规格书自己的排序是对的，坚持它即可）。

### 4.4 存档编辑器 region 读写
**总判：✅ 全规格书里我最放心的技术点。** MCA 格式（512B 扇区表 + zlib chunk）公开且稳定多年；"字节级搬运不深解析"（431 行）是正确的工程降维——跨存档粘贴不需要理解方块数据，只需要 1.18 前后两种 NBT 顶层包裹结构的识别与坐标字段重定位（实体 Pos/双精度、方块实体坐标、计划刻位置——规格已枚举完整）。备份 zip + 失败回滚是文件操作。唯一要小心的：**扇区表项清零后 region 文件的空洞回收**（删除区块不缩文件）与 **1.18 前 Level 包裹层的嵌套坐标字段路径**需要逐版本核对；建议实现时先写 region 读写单元测试（含损坏文件容错）再写 UI。

### 4.5 地区闸实现
**总判：✅ 实现本身简单，风险在口径而非代码。** 双信号判定（`Locale.getDefault().getCountry()` + `TelephonyManager.getNetworkCountryIso`/SIM MCC）+ 双失败默认大陆，是 8/444 行的明确规格，工程量以天计。三个口径问题必须先答：① 大陆判定后"入口隐藏 + 动作拒绝"（8 条）对哪些功能生效（8 条列了下载/联机/资源，那 XyeBBS 检索展示呢？444 行说检索与展示全球可用——两句合读是自洽的，但要在代码里把"动作"精确到下载/安装点击）；② P-4 的模块安装是否受闸；③ 判定信号在无 SIM 平板/WiFi-only 设备上退化为单信号，"失败默认大陆"会让无 SIM 的海外平板也被判大陆——这是**合乎合规保守方向的**，但要在验收清单里标注这是预期行为而非 bug。

### 4.6 开发者选项 13 分区工作量
**总判：⚠️ 总量大但平坦，无单点技术风险，纯工作量约等于一个中型功能模块。** 13 分区里 A/B/G/H/I/J/M 是信息聚合（每区 1–3 天）；C/L 依赖游戏底座与游戏端数据暴露（P-2），必须排在底座之后；D 依赖模块系统完成；E/K 依赖下载器与性能埋点。分期（5.3 节迭代 1 = A–D、F–J；迭代 2 = E/K/L/M）合理。建议把 D 区"隔离记录（L1–L5 哪层拦下）"的日志结构在模块系统设计期就定好（事件 schema），否则事后补埋点是返工。

## 五、我认为主 Agent 最可能犯的错误或漏判

按可能性排序：

1. **漏掉 P-2（启动底座缺位）**：59 条逐条列清单时，"JRE/渲染器/游戏进程底座"没有自己的条目号，逐条对表极容易全部 ✅/⚠️ 走完却没发现整栋楼的地基没有规格条目。这是逐条评估法的系统性盲点，lead 大概率同样逐条对表，可能同盲。**这是我预测的最大分歧点：如果 lead 的清单没有单独把"启动底座"拎成最高风险项，它漏了。**
2. **把 39（AI 工坊）判成 ✅**：链路六环节看着都"成熟"，但把"用户 GitHub 账号授权 + BYOK key + 手机端推送"三个外部前置隐含为已满足。正确判定是 ⚠️ 且附外部条件清单。
3. **低估 17/53 的索引托管与国内可达性矛盾**（P-3/P-4）：字面照抄规格书，不会发现"GitHub Release 官方索引"与"国内为主用户"的冲突。
4. **照抄 2.3 的 optimizedDir/chmod 兜底方案而不质疑其在 Android 10+ 的有效性**（P-7）：这段文字是规格书里少数"写得很具体但可能过时"的技术细节，具体到让人不怀疑它。
5. **把 L2 崩溃隔离写成 try-catch 包装 Composable 就完事**：漏重组异常与协程异常两条传播路径，单测全绿但真机上模块崩溃仍然带崩宿主。
6. **对 46 条 <10ms 给出静态"可达成"结论**：不建基线测量就承诺数字指标。
7. **环境障碍列表写一半**：题设环境缺 Android SDK/NDK/Gradle/Node，但若 lead 检查工具链时可能**漏掉 Rust**（Nucleation 需要）与 CMake/Ninja（cubiomes 需要，NDK 自带但要点名启用）。以及 **Windows 长路径 + 中文目录名**（工作目录 `C:\Users\Administrator\Desktop\Vaelin Launcher` 含空格，Gradle/NDK/CMake 对含空格路径偶发问题，建议工程实际落盘到无空格无中文路径——这是经验性风险，未验证具体工具版本是否已免疫）。

## 七、结论一句话

**59 条中没有技术性死局；最大的问题不是"能不能做"，而是规格书把整栋楼最重的一层地基——MC Java 启动底座——当成了看不见的既成事实，且三条官方功能（39/38/23）共同悬挂在用户尚未提供的外部凭据上。** 需求确认阶段应优先裁决：底座实现边界、索引托管与地区闸口径、外部凭据清单。
