## 0. 一句话架构

**Vaelin = 一个 Compose 宿主外壳 + 一个从上游开源底座借来的 MC Java 运行时 + 一套只认 `lab-api` 的模块容器。**
三者边界必须硬隔离：底座负责"游戏能跑"，宿主负责"界面与模块调度"，模块负责"跑起来之后的体验"。

任何架构决策如果让这三层互相渗透，都会在第 12–23 条（模块系统）上返工。

## 1. 分层

```
┌──────────────────────────────────────────────────────────┐
│ app（Compose UI 层，Java/Kotlin）                          │
│  · 导航容器 NavHost / LabModulePage(moduleId, route)      │
│  · FeatureRegistry · ModuleErrorBoundary · 安全模式        │
│  · 设置 / 下载 / 账号 / 开发者选项(:dev-options 仅 Beta)   │
├──────────────────────────────────────────────────────────┤
│ lab-api（独立 Gradle 模块，纯 Kotlin + Compose 运行时）     │
│  · LabModule / LabHost / LabPage / UiExtension / 版本协商  │
│  · 编译期只暴露接口，零业务实现                             │
├──────────────────────────────────────────────────────────┤
│ core 层（Kotlin，无 Compose 依赖）                         │
│  · module-loader（DexClassLoader + 懒加载 + L1–L5）        │
│  · module-index（索引 DB、SHA256、apiVersion 校验）        │
│  · worldtools（region / NBT / 投影 / 种子）                │
│  · downloader · source-gate · region-gate                 │
├──────────────────────────────────────────────────────────┤
│ runtime 层（MC Java 运行时，**来自上游，不重写**）          │
│  · Android 版 JRE（OpenJDK 8/17/21 移植）                  │
│  · 图形翻译层 GL4ES / VirGL / Zink / HGL                   │
│  · 音频 OpenAL · 输入注入 · 进程/挂载（PRoot 或等效）      │
├──────────────────────────────────────────────────────────┤
│ native 层（NDK 编译，arm64-v8a）                           │
│  · libcubiomes.so（种子地图）                              │
│  · libnucleation.so（投影网格化，Rust→C FFI→JNI）           │
└──────────────────────────────────────────────────────────┘
```

**关键约束**：`lab-api` 不得依赖 `app`；`core` 不得依赖 Compose；`runtime` 层只通过稳定接口被调用，模块永远看不到它。

## 2. 最大的一个缺口：启动底座（规格书未定义）

规格书 59 条里，32 联机、31 悬浮、42-C/L 区、34 游戏内查看器、35 游戏内查看器都建立在"游戏已经能跑"之上，但**没有任何一条定义这个底座**。而在 Android 上让 MC Java 版跑起来，需要同时解决五件事：

| 组成 | 作用 | 从零自研的代价 |
|---|---|---|
| Android 版 JRE | MC 是 JVM 程序，Android 无 Java SE | 需交叉编译 OpenJDK（8/17/21 三代），数年维护 |
| 图形翻译层 | MC 用 OpenGL 桌面版，Android 只有 GLES | GL4ES / VirGL / Zink / HGL，每条都是独立大项目 |
| 音频层 | OpenAL 软实现 | 中等 |
| 输入注入 | 键鼠/触屏映射到游戏 | 中等 |
| 进程隔离/挂载 | 游戏文件系统与 Android 沙盒隔离 | PRoot 或应用私有挂载 |

**这一层的工作量大于规格书其余所有条目之和。** 因此必须由用户裁决边界，见下节三个选项。

## 3. 启动底座的三个选项

### 选项 A：复用上游开源底座

直接依赖 PojavLauncher / FoldCraftLauncher / ZalithLauncher2 的 runtime 组件（JRE 移植、图形翻译层、输入注入），Vaelin 只写自己的 Compose 外壳与模块系统。

**先把这个选项的真正前提说清楚，不做辩护**：规格书第 5 行原文写的是参考项目——含"Pojav 系启动器、FCL、ZL2"——"**仅作参考**……不 Fork 他人仓库、不以他人 APK 为基底"。选项 A 是**链接依赖**这些 runtime 组件，不是"参考"。**链接使用是否落在第 5 行的禁止范围内，规格书没有回答，这是用户级的规格裁决，不是技术裁决。**（我在此前的版本里拿 cubiomes/schematic4j 作类比说"规格书自己也引用源码"，这个类比不成立——那三项是第 5 行**点名允许源码引入**的，Pojav 系 runtime 不在点名允许之列。类比已撤回。）

如果用户裁决允许，技术侧的代价与收益是：

- **合规代价**：上游为 GPL-3.0（Pojav / FCL / Zalith 三家 LICENSE 已读）。Vaelin 模块模板本就强制 `GPL-3.0`（规格书 6.1），因此**项目整体按 GPL-3.0 开源**时链接上游完全合规，只需在"关于"页与仓库标注来源与许可。即：GPL 传染的代价与规格书已有的模块生态许可设定是自洽的。
- **收益**：这是唯一能让"种子地图完成即发布"（第 51 条）成立的路。
- **其它代价**：必须跟进上游的 Android 版本适配；上游代码风格与 Compose 全 UI 的边界需要划清。

### 选项 B：从零重写底座
- **代价**：JRE 交叉编译 + 图形翻译层自研，等于重做 Pojav 数年工作量。首版发布不可达。
- **结论**：技术上不可达，除非用户明确要求"零上游代码"并接受首版范围大幅收缩。

### 选项 C：只做非游戏功能（放弃"启动器"定位）
- 只做种子地图/投影/存档等世界工具，不做游戏启动。
- 与第 1 条产品定位（启动器）冲突，与第 51 条里程碑冲突。
- **结论**：不成立。

> **待用户裁决（原文呈报，不预设答案）**：
> 规格书第 5 行「参考项目仅作参考、不 Fork 他人仓库、不以他人 APK 为基底」，是否允许 Vaelin **以 Gradle 依赖方式链接** Pojav 系 / FCL / ZL2 的 runtime 组件（而非仅阅读其源码自行实现）？
> - 若允许 → 走选项 A，项目整体 GPL-3.0 开源。
> - 若不允许 → 走选项 B，首版发布条件（第 51 条）不成立，需要重新定义首版范围。
>
> **在裁决前，第 31、32、34⑥、35⑥、42-C/L、51 一律标为"依赖底座裁决"。**

## 4. 模块系统实现方案（规格书 102–221 行几乎可直接翻译）

### 4.1 三类扩展点
| 类型 | 内容 | v1 范围 |
|---|---|---|
| Lab 页面 | `registerLabEntry` → 宿主 `LabModulePage(moduleId, route)` | 完整 |
| UI 扩展 | `LAB/SIDEBAR/TOP_BAR/SETTINGS/THEME/HOME` 六类**声明式** | 完整（不提供往宿主既有页面塞 Composable） |
| 游戏内页 | `registerInGamePage` | 只定契约，不实现 |

**导航容器化**：模块自己的多页用模块内部 Compose 状态栈，宿主只提供固定容器路由与返回键桥接。**禁止模块碰宿主 NavDisplay**（会报 Unknown screen）。

### 4.2 加载链路
```
启动 → 读索引 DB（仅 id/version/startup，不读 dex）
     → startup=true 的进空闲线程预加载（不阻塞首帧）
     → 用户首次进入模块界面
     → DexClassLoader(dex, optimizedDir=私有目录, librarySearchPath, parent=宿主 classloader)
     → 反射实例化 entryClass → onLoad(host) → onEnable
```
**类空间隔离**：`parent` 必须是宿主 classloader（保证模块能用 `lab-api` 与 Compose 运行时），但这意味着两个模块各带同名工具类会互相遮蔽。**规则**：模块间只经 `host.getService(id, Interface::class)` 通信，禁止依赖"宿主 classloader 里恰好有某个类"。

#### R2 硬约束：targetSdk ≥ 34 时模块 dex 必须只读（必须先处理，否则第一次真机就爆）

Android 14（API 34）起禁止应用对动态加载的代码持有可写权限，官方原文在 `developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading`。上面的链路里有一处致命嵌套：模块 zip 解压到私有目录后，解压出来的 `.dex` 默认可写，此时 `DexClassLoader` 会**直接加载失败**，而不是降级。

处置（写进安装器的实现约束，不是"注意事项"）：

1. 解压完成后立即对 dex 及装载目录内所有 `*.jar`/`*.dex` 调 `File.setReadOnly()`，并对目录本身置 `setWritable(false)`；
2. 加载前复查一次（防止中间有人改了权限）；
3. 只有「卸载」与「升级重装」两条路径才临时恢复写权限，其余任何时刻不得可写；
4. 开发者选项 D 区（第 42 条）的"清 dexopt 缓存"要严格区分两类对象：系统管理的 odex/vdex 目录**可清理**，模块的 dex 源文件**永远不可写**——这条不写清，D 区调试功能会反过来触发加载失败。

这条属于 P0，不属于"文档里的注意事项"。

#### optimizedDir 的落点

R2 的直接推论：`optimizedDir` 应放 `codeCacheDir` 而不是 `filesDir`——避免 dexopt 产物计进用户数据配额，也避免与只读约束互相干扰。

### 4.3 崩溃隔离 L1–L5 的真实难点
| 层 | 机制 | 陷阱 |
|---|---|---|
| L1 | 调用期 try-catch | 只覆盖直接调用 |
| L2 | Compose ErrorBoundary | **重组期异常不经过 try-catch**：必须用子组合 + 状态捕获拦；协程异常走 `CoroutineExceptionHandler`，是第二条独立路径 |
| L3 | 单模块崩溃计数达阈值自动禁用 | 计数要按模块隔离持久化 |
| L4 | 连续两次异常退出 → 自动安全模式 | 需崩溃标记写入时机早于 UI |
| L5 | static shortcut | 见 §4.5 |

### 4.4 native 库加载（规格书 2.3 的 `chmod 0o755` + `System.load` 在新系统上不成立）
Android 10+ 的 SELinux 对"应用可写目录里的 .so 被 dlopen"有 W^X 限制，规格书这段是旧 ROM 经验。**可行路径**：

1. **把 cubiomes 等 native 库放进宿主 APK 的 `jniLibs/arm64-v8a/`** —— 由 `ApplicationInfo.nativeLibraryDir` 提供，系统保证可加载。这条路最稳，代价是这些库不能随模块热更。
2. 需要热更的 native 模块（如 Nucleation）走**独立 APK 安装**：宿主用 `createPackageContext(pkg, 0).applicationInfo.nativeLibraryDir` 拿到对方的合法 native 目录，加入 `DexClassLoader` 的 `librarySearchPath`。
3. `chmod 0o755` + `System.load` 只作为老 ROM 兜底，**不作为主路径**。

> 该项需 arm64 真机实测关闭，标未验证。

### 4.5 安全模式
- `res/xml/shortcuts.xml` **static** 声明（dynamic 会被 `ShortcutManager` 运行时删除）
- Intent 带 `safe_mode=true`
- `Application.onCreate()` 最早期置 `ModuleLoader.globalSkip = true`
- `safe_mode_active` 持久化，普通重启不清除
- `crash_count ≥ 2` → `auto_safe_mode = true`
- 该开关**不进 FeatureRegistry**，不可被启动器内代码增删

### 4.6 模块系统的五组验证实验（E1–E5，P0 第一周，先于一切模块功能代码）

这一节的由来：**"模块 APK 打包 Compose UI、运行时共享宿主 Compose runtime"这条路线，目前没有任何可公开核实的先例**（调研结论 R3）。规格书第 7 + 13 + 14 + 17 条要求的正是这条路。在投入功能开发前，必须先用最小工程把它证伪或证实，否则整个模块 UI 设计可能要在中期推翻。

| 实验 | 目的 | 做法 | 判据 |
|---|---|---|---|
| **E1** dex 权限阴性对照 | 证明 R2 的约束真实存在 | 同一模块 dex，对照组保持可写、实验组置只读，各加载一次 | 对照组失败、实验组成功 → 约束成立，R2 处置有效 |
| **E2** Compose runtime 共享主实验 | 判定路线生死 | 宿主 APK 内放一个 `@Composable` 模块，模块 jar 里 `compileOnly` androidx.compose.*，运行时用宿主 classloader 加载并渲染 | 能正常渲染且无 `NoClassDefFoundError` / 版本方法缺失 → 路线可用 |
| **E3** 同名类委派遮蔽 | 验证类空间规则 | 两个模块各带一个同名工具类，交替加载 | 确认行为，据此固化"模块间只走 getService"的规则 |
| **E4** 相邻 Compose BOM 版本漂移矩阵 | 决定 apiVersion 是否需要绑 BOM | 用 BOM N 编译模块，在 BOM N±1 的宿主上加载 | 若崩溃 → `module.json` 必须增加 Compose 编译器/元数据兼容声明，或把 apiVersion 语义显式绑定 BOM 版本 |
| **E5** 重组异常 + 协程异常双路隔离 | 验证 L2 | 分别在 `@Composable` 重组期抛异常、在 `viewModelScope` 协程里抛异常 | 两条路径都被 `ModuleErrorBoundary` 捕获且宿主不崩 |

**E4 的结论有产品级后果**：如果 Compose 版本漂移会导致模块崩溃，那么宿主每次升级 Compose BOM 都会打断整个模块生态——这必须在第 23 条的 CI 三检之外再加一条检查，或者把 apiVersion 的定义从"lab-api 版本"扩展为"lab-api 版本 + Compose 编译器协议版本"。规格书第 23 条目前只查"无 androidx/compose/ 类 + apiVersion 匹配"，**不足以覆盖这个耦合**。

**E2 若失败，替代路径**：模块自带一份 Compose（代价：5MB dex 红线与第 46 条冲突，且多副本内存开销），或模块 UI 限制为宿主提供的声明式扩展点（放弃 LabPage 的自由 Composable）——后者会削弱第 12 条"模块是完整能力载体"。所以 E2 必须第一个做。

## 5. 世界工具三件套

### 5.1 种子地图（核心卖点，第 34 条）
```
Kotlin UI (Compose Canvas 瓦片)
   ↕ JNI
libcubiomes.so  ←  02-参考源码/cubiomes 源码直接编入（MIT）
```
- 源码已落盘 `02-参考源码/cubiomes`（35 文件，MIT）。**不引用它自带的 CMakeLists**（会额外产 SHARED 目标），在自己 `native/CMakeLists.txt` 里 `add_library(cubiomes STATIC ...)` 列出 `.c` 文件。
- JNI 7 接口：`init / biomeAt / renderTile / findFeatures / findSpawn / scanOres / release`
- UI 侧：256px 瓦片、`TILE_SCALES=[1,4,16,64,256]`、LRU 32、并发 2、渐进渲染 `fallbackTileScale`
- 群系着色放在 C 侧（一次算完整块 RGBA，比 JNI 逐点调用快两个数量级）
- **Axolotl 验证过的做法**：主图 Canvas 2D + C 侧 `biomesToImage` 产 RGBA。Android 上等价物是 Compose `Canvas` + `ImageBitmap`。
- **额外纪律**：必须把"引擎 revision 常量"在一处定义、多处引用（Axolotl 因为 C/Rust/前端/映射表四处各写一份而踩过坑）

### 5.2 投影工坊（第 35 条）
- `.litematic` / `.schem`（Sponge v2/v3）/ `.schematic`（Legacy MCEdit）
- **注意**：Axolotl 明确拒绝 `.schematic`（`schematic-preview` 模块第 613–617 行），而规格书要求三格式，**这部分没有现成参考，要自己做**。
- 网格化：Nucleation（Rust）+ greedy meshing → C FFI → JNI
- 内存纪律（数值来源：Axolotl v1.10.5 投影模块的实测阈值，读自用户提供的 `axolotl-research` 调研报告；**Axolotl 源码本身没有拉进 `02-参考源码/`，因此这是二手数值，不是从源码核对的**）：文件 ≤ 256 MiB、解压后 ≤ 512 MiB、方块总数 ≤ 1.28×10⁸、palette 条目 ≤ 1,048,576、可编辑方块 ≤ 250,000。Vaelin 可直接沿用这套量级作首版护栏，但需在真机上重新标定（Android 堆上限比桌面低一个数量级，256 MiB 文件很可能要先降）
- 流式：分块加载 + 顶点缓冲上限，避免大投影 OOM

### 5.3 存档编辑器（第 36 条）
- MCA region：512 字节扇区表 + zlib；删除区块 = 位置表项清零
- 跨存档粘贴：字节级搬运 + 坐标重映射（实体 double、方块实体 int、计划刻），**不深解析方块数据**
- 1.18 前 `Level` 包裹层 与 1.18 后拍平层两种布局都要认
- 自动备份 zip 存旁，失败可回滚
- 2D 区块选择界面复用种子地图瓦片基建

## 6. 合规与闸

### 6.1 地区闸（第 8/25 条）
- 双信号：`Locale.getDefault().getCountry()` + SIM 国家码（`TelephonyManager.getNetworkCountryIso`）
- 双信号都失败 → **默认按大陆**
- **闸只建在"文件分发动作"上**（下载/安装），检索与展示信息全球可用
- **必须补一条口径**（规格书未写）：模块索引/模块安装是否受闸。按"模块是产品心脏"的原则，应**不受闸**，闸只覆盖游戏内容分发。

#### 地区闸的权限流程（规格书完全没写，但这是已锁条目 8/25 落地的第一道坎）

`getSimCountryIso` 与 `getNetworkCountryIso` 在 Android 10+ 都需要 `READ_PHONE_STATE` 运行时权限（后者是官方 commit 明确加的）。规格书只说"双信号判定、失败默认大陆"，没有一个字讲权限怎么要。这件事必须设计，不能留给实现者临场发挥：

| 决策点 | 建议方案 | 理由 |
|---|---|---|
| 何时请求 | **不在首启弹**。首次进入"下载/联机"相关入口时才请求，且先展示一句说明 | 启动器一上来要电话权限，用户体验与商店审核都是雷 |
| 拒绝算什么 | **等同于信号失败 → 默认按大陆处理** | 合规上只有保守这一个方向是对的；不能因为用户拒绝权限就放行 |
| 拒绝后是否还显示入口 | 隐藏入口（与大陆处理一致） | 一致性优先于可发现性 |
| 系统地区（第二信号） | `Locale.getDefault().getCountry()`，无需权限，永远可得 | 保证至少有一个信号可用 |
| 权限被永久拒绝 | 提供"去设置"引导，但不做反复弹窗 | 不骚扰 |

**这条也进 P0**：因为它是已锁条目，不是可选项。

| Pojav / FCL / Zalith | GPL-3.0 | 仅在底座选项 A 被用户裁决允许时才发生链接；此时项目整体 GPL-3.0 |

**Terracotta 的三条出路（第 32 条联机必须选一条，不能悬空）**：
1. **优先走 EasyTier 路线**（LGPL-3.0，且官方自带 Android JNI 绑定与 VPNService 参考实现）——推荐；
2. Terracotta 只读代码学协议、自行实现协议（"参考"不触发 copyleft）——工作量中等；
3. 若必须用 Terracotta-lib，把它做成**独立的 AGPL 模块 APK**，经模块服务注册表交互——模块体系恰好为此而生，但"动态加载是否阻断 copyleft 传染"属法律灰区，**这不是法律结论，必须由用户判断**。

必须产出"参考项目许可核实清单"，逐个仓库核对 LICENSE 文件（不能只看 README 声明）。目前 `02-参考源码/` 里已核对 LICENSE 原文的是 cubiomes、schematic4j；其余仓库的 LICENSE 需在源码落盘后逐一读原文。

1. **P0 骨架 + 五组实验**：Gradle 工程、`lab-api` 契约、导航容器、FeatureRegistry、懒加载、索引 DB；以及 **§4.6 的 E1–E5（先于任何模块功能代码）** 和 **§6.1 的地区闸权限流程**、**§4.2 的 dex 只读约束**

### 8.1 必须现在拍板的范围裁剪：首版种子地图不含游戏内查看器

## 9. 待用户裁决项（阻塞架构定稿）

### 9.1 第一项（唯一真正的闸门）：启动底座边界 = 第 5 行「仅作参考」如何解释

**这两条不能拆开问**——它们是同一个选择的两个面，拆开会让用户对同一件事答两次：

> 规格书第 5 行「参考项目仅作参考、不 Fork 他人仓库、不以他人 APK 为基底」，是否允许 Vaelin 以 Gradle 依赖方式**链接** Pojav 系 / FCL / ZL2 的 runtime 组件？若允许，则项目整体按 **GPL-3.0** 开源（模块模板已强制 GPL-3.0，两者自洽）。

- 允许 → 选项 A，第 51 条成立，首版可达。
- 不允许 → 选项 B，从零重写 JRE + 图形翻译层，第 51 条不成立，首版范围必须重定义。

**为什么它排第一，而且真正的原因不是许可**：底座是 P0→P1 的关键路径闸门。而且它至今**卡在物质前提上**——Pojav/FCL/ZL2 三个 runtime 仓库的源码还没完整落盘（gh-proxy 对大仓库 archive 会在打包阶段卡成 0 字节）。裁决之前拿不到组件，裁决之后才开始下载，"纸面裁决换不来开工条件"。所以这个裁决项必须附带一条执行承诺：裁决通过的当天就要用可用的通道把上游源码取全。

### 9.2 第二项：模块索引托管位置
GitHub Release + 镜像 / 自有对象存储。建议 GitHub Pages 作主 + 国内镜像双源 + 索引 JSON 签名校验。与"国内为主"的目标用户定位直接相关，不能默认 GitHub 直连可用。

### 9.3 第三项：第 33 条「正版上传」是否保留
规格书没有账号体系条目（见 `01` §四 G-7）。保留则必须新增一条未在 59 条里出现的"Microsoft 账号登录"子系统；不保留则第 33 条降级为本地皮肤编辑 + 3D 预览。
