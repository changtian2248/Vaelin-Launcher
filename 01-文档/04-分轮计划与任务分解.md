## 1. 决策演进：从 Pojav 到 ZL2

用户的判断经过四轮收窄，最终落点与最初设想不同，这里按时间顺序写清楚，避免以后翻案时找不到依据。

**第一轮（m00860）**：启动基底直接抄 Pojav，并要兼容它的插件。
用户原话：「启动基底直接抄Pojav，并且要兼容他的插件……我建议进行分轮。」

**第二轮（m00882）**：插件指渲染器包；Java 启动进程必须照抄 Pojav；UI 层自写；APK 从零新建。
用户原话：「JAVA的启动进程一定要抄这个，因为手机端只有它能用，或者说它这个方案是最好的。所有人都在用，所以我们不要用别的。启动器提供的功能，UI层才要我们进行构写，注意这个apk我们要从零开始写。当然你也可以上网去找一些壳进行套。」

**第三轮（m00935）**：允许改用 ZL2。
用户原话：「虽然游戏的启动基底让你去抄他的，但是如果你对他的协议不满意，你可以去抄同样使用Pojav启动逻辑的ZL2等这些启动器。」

**第四轮（m00951 / m00956）**：定案。
- 渲染器协议：**直接抄 ZL2，接受整个项目 GPL-3.0**
- 启动基底：**以 ZL2 为准，拿它的多进程与 JvmService**
- 许可态度（原话）：「我对协议这一个东西不是很在意，总之属于开源协议就行。」

**为什么这不算推翻前几轮**：ZL2 的启动核心就是 Pojav 的 native 层。`02-参考源码/ZalithLauncher2/ZalithLauncher/src/main/AndroidManifest.xml` 与 `jni/` 已核实，其 `jre_launcher.c`、`java_exec_hooks.c`、`input_bridge_v3.c`、`awt_bridge.c`、`egl_bridge.c`、`sdl_hook.c`、`exit_hook.c`、`lwjgl_dlopen_hook.c` 与 Pojav 同源；ZL2 README 也写明「项目使用 PojavLauncher 作为启动核心」。所以「抄 ZL2」= 「抄 Pojav 启动核心」+ 多进程架构 + 7 个渲染器 + 141 个 Java/Kotlin 文件组成的 Compose 壳。用户第二轮的硬要求仍然满足。

**规格书已同步为 v1.2**（`01-文档/spec/Vaelin-全量规格书.md`）：第 5 行、第 6 条、第 9 条三处改动，并新增 v1.2 修订记录块。第 7 条「UI 全面 Compose」与「UI 层自写」**仍未改动**。

## 2. 渲染器协议：从硬编码 switch 升级为插件化

### 2.1 Pojav 的做法（原方案）

`02-参考源码/PojavLauncher/app_pojavlauncher/src/main/java/net/kdt/pojavlaunch/utils/JREUtils.java:463-486` 是一个硬编码 switch，三种渲染器对应三个固定文件名，加新渲染器必须改源码重编。它的价值是**兼容面明确**：任何渲染器包只要按这三个名字投放就能被加载。

### 2.2 ZL2 的做法（新方案）

`02-参考源码/ZalithLauncher2/ZalithLauncher/src/main/java/com/movtery/zalithlauncher/game/renderer/RendererInterface.kt`（83 行）定义 15 个成员：

| 成员 | 作用 |
|---|---|
| `getRendererId()` / `getUniqueIdentifier()` | 显示 id 与持久化唯一键 |
| `mesaBased` / `needsZinkDriverOverride` / `supportsSfpewByDefault` | 三能力开关 |
| `getRendererName()` / `getRendererSummary()` | 名称与说明 |
| `getMinMCVersion()` / `getMaxMCVersion()` | MC 版本窗口 |
| `getRendererEnv(): Lazy<Map<String,String>>` | 该渲染器需要的环境变量 |
| `getDlopenLibrary(): Lazy<List<String>>` | 需预先 dlopen 的库清单 |
| `getRendererLibrary()` / `getRendererEGL()` | 主渲染库与 EGL 库名 |

配套三件：
- `Renderers.kt`（114 行）：注册表。内置 7 个（`NGGL4ESRenderer` / `GL4ESRenderer` / `KopperZinkRenderer` / `MobileGluesRenderer` / `VirGLRenderer` / `FreedrenoRenderer` / `PanfrostRenderer`），`addRenderer` 冲突检测，`setCurrentRenderer(uniqueIdentifier, retryToFirstOnFailure=true)` 找不到时回退首个，`getLegacyRendererIds()` 做配置迁移。
- `RendererPlugin.kt`（49 行）：外部插件包实现同一接口，携带 `packageName` / `displayName` / `summary` / `minMCVer` / `maxMCVer` / `glName` / `eglName` / `env` / `dlopen` / `isConfigurable`。
- `plugin/renderer_v2/` 与 `renderer/config/`：配置 DSL 与解析器，让插件渲染器可以带自己的参数表单。

### 2.3 兼容 Pojav 生态怎么落

这里有一个**必须先讲清楚的冲突**：ZL2 的渲染器 id 沿用了 Pojav 的命名（`opengles2` / `opengles3` 等），但它指向的库**不是同一个**。逐文件核实后的真实映射：

| ZL2 内置渲染器 | `getRendererId()` | `getRendererLibrary()` | `getRendererEGL()` | mesaBased |
|---|---|---|---|---|
| `GL4ESRenderer` | `opengles2` | `libgl4es_114.so` | — | false |
| `NGGL4ESRenderer` | `opengles3` | `libng_gl4es.so` | — | false |
| `KopperZinkRenderer` | `opengles3_desktopgl_zink_kopper` | `libglxshim.so` | `libEGL_mesa.so` | true |
| `MobileGluesRenderer` | `opengles3_mobileglues` | `libmobileglues.so` | `libmobileglues.so` | false |
| `VirGLRenderer` | `gallium_virgl` | `libOSMesa_2121.so` | — | true |
| `FreedrenoRenderer` | `gallium_freedreno` | `libOSMesa_8.so` | — | true |
| `PanfrostRenderer` | `gallium_panfrost` | `libOSMesa_2300d.so` | — | true |

Pojav 那一套（`JREUtils.java:463-486`）：

| Pojav 渲染器 id | 库 |
|---|---|
| `opengles2` / `opengles2_5` / `opengles3` | `libgl4es_114.so` |
| `vulkan_zink` | `libOSMesa.so` |
| `opengles3_ltw` | `libltw.so` |

**三处实质冲突**：
1. **同名不同库**：`opengles3` 在 Pojav 是 `libgl4es_114.so`，在 ZL2 是 `libng_gl4es.so`。按 id 复用会静默换掉用户预期的渲染器。
2. **Pojav 的 zink 在 ZL2 里没有对应**：Pojav 是 `vulkan_zink → libOSMesa.so`，ZL2 的 zink 走 Kopper（`libglxshim.so` + `libEGL_mesa.so`），是另一条实现路径。ZL2 的 OSMesa 是按版本分的三个文件（`libOSMesa_8` / `_2121` / `_2300d`），没有单一的 `libOSMesa.so`。
3. **ZL2 完全没有 LTW**：`renderers/` 七个文件里搜 `ltw` 零命中，`libltw.so` 不存在。

**因此兼容方案不是"映射"，而是"并存"**——ZL2 的七个原样保留，另外补三个 Pojav 兼容实现，用 Pojav 的 id 与库名：

| 新增薄实现 | id（沿用 Pojav） | 库 | EGL / 环境 |
|---|---|---|---|
| `PojavGL4ES25Renderer` | `opengles2_5` | `libgl4es_114.so` | — |
| `PojavZinkRenderer` | `vulkan_zink` | `libOSMesa.so` | 需在 T1.3 从 JRE 包确认实际文件名 |
| `PojavLTWRenderer` | `opengles3_ltw` | `libltw.so` | `POJAVEXEC_EGL=libltw.so` |

这样两套生态共存且 id 不撞。每个薄实现约 15–20 行，全是 getter。

加载顺序沿用 Pojav 的三段式：裸名 `dlopen` → `findInLdLibPath` → `NATIVE_LIB_DIR` 绝对路径；失败回退 gl4es。这样既保留旧渲染器包可用，又让新插件包能通过 `RendererPlugin` 接入。

**待验证（放第 1 轮 T1.3）**：① `libgl4es_114.so` 与 `libOSMesa.so` 是否真在 JRE 包 `lib/` 内、`libOSMesa.so` 到底叫什么；② LTW 的 `.aar` 解出的 `.so` 名是否就是 `libltw.so`。本轮未下载 JRE 包（几十 MB 且不含源码），标为未验证。

### 3.1 规模实测

| ZL2 `jni/` 子目录 | `ctxbridges/`(16)、`jsound/`(29)、`GL/`(3)、`flite/`(3)、`driver_helper/`(3)、`linkerhook/`(2)、`logger/`(2)、`environ/`(2)、`awt_xawt/`(1) |
| ZL2 启动核心类 | `Launcher.kt`(531) / `GameLauncher.kt`(566) / `LaunchArgs.kt`(385) / `GameLaunchFlow.kt`(288) / `RuntimesManager.kt`(291) / `GameHandler.kt`(228) / `JvmService.kt`(183) / `MCOptions.kt`(157) / `JvmLauncher.kt`(147) / `JVMSocketServer.kt`(118) / `UnpackJreTask.kt`(98) / `ZLBridge.java`(82) |

### 3.2 判定原则

**「把 JVM 拉起来并渲染出画面」之前的全部环节复用；「用户看到并操作的一切」自写。**

### 3.3 复用（进 `startup-core` 模块，保留 GPL-3.0 与原版权声明）

| 范围 | 代表文件 | 作用 |
|---|---|---|
| JNI 桥 | `bridge/ZLBridge.java`、`ZLNativeInvoker.kt`、`NativeLibraryLoader.java`、`ZLBridgeStates.kt`、`LoggerBridge.java` | Java 与 native 的调用通道、库加载 |
| native 层 | `jni/jre_launcher.c`、`java_exec_hooks.c`、`input_bridge_v3.c`、`awt_bridge.c`、`egl_bridge.c`、`sdl_hook.c`、`exit_hook.c`、`stdio_is.c`、`vulkan_checker.c`、`utils.c`、`bigcoreaffinity.c`、`lwjgl_dlopen_hook.c`、`sdl_dlopen_hook.c` + 全部子目录 | EGL/GL 桥、JVM 拉起、输入注入、音频、大核绑定 |
| 启动调度 | `launch/Launcher.kt`、`GameLauncher.kt`、`LaunchArgs.kt`、`GameLaunchFlow.kt`、`JvmLauncher.kt`、`JvmLaunchInfo.kt`、`handler/`、`LibSortFix.kt`、`MCOptions.kt` | 参数组装、资源校验、类路径排序、启动流程 |
| 安装器 JVM 进程 | `game/download/jvm_server/JvmService.kt`、`GameJVMRunner.kt`、`JVMSocketServer.kt`、`ProcessLogTailer.kt`、`JvmCrashException.kt`、`_JvmService.kt` | **注意：`:jvm` 进程服务于下载/安装期的 JVM**（跑 Forge/NeoForge installer jar），不是游戏运行进程。调用方只有 `GameJVMRunner` 与 `GameInstaller.kt:574` |
| 运行时管理 | `multirt/RuntimesManager.kt`、`Runtime.kt`、`components/jre/UnpackJreTask.kt`、`UnpackJnaTask.kt` | 多 JRE 版本解压与管理 |
| 渲染器 | `renderer/RendererInterface.kt`、`Renderers.kt`、`RendererPlugin.kt`、`renderers/` 七个、`plugin/renderer_v2/`、`renderer/config/` | 插件化渲染器协议与注册表 |
| 日志与崩溃 | `utils/logging/`、`LoggerBridge.java` | 游戏日志落盘与读取 |

**游戏到底跑在哪（已实测，此前的判断有误）**：

`VMActivity` 在 Manifest 里挂 `android:process=":game"`（`AndroidManifest.xml:119-124`），它的 `initSession()` 里构造 `GameLauncher(activity = activity, ...)`（`VMActivity.kt:227`），JVM 由 `:game` 进程内的 native launcher 拉起。所以：

- **游戏隔离 = `:game` 进程级**，不是 `:jvm`
- `JvmService` / `JVMSocketServer` 那套 UDP 回报机制，复用价值在**安装器**（`GameInstaller` 装 Forge/NeoForge 时要等 installer jar 跑完并拿退出码），不在游戏

### 3.3.1 边界模糊项：`GameHandler.kt` 是混合体

`GameHandler.kt`(228 行) 不能整体划入复用：`:61` 构造参数收 `val activity: Activity`、`:96` `MCOptions.setup(activity)`、`:231` 还有个 `@Composable fun ComposableLayout()` 直接调 ZL2 的 `GameScreen`。

判定：**输入桥接、`SdlBridge`、Terracotta 相关逻辑复用；Activity 绑定与 Compose UI 绑定自写。** T1.1 逐文件判定时要把它拆成两半标。

### 3.4 不复用（Vaelin 自写）

- 全部 UI 层：ZL2 的 `ui/activities/`、`ui/screens/`、`ui/components/`、`ui/theme/` 等 Compose 页面——Vaelin 的产品气质与信息架构不同，且规格书第 37 条要求玻璃 UI 模块化。
- **游戏画面宿主层**：`VMActivity` 的 Compose 部分与 `GameScreen`，连同 `GameHandler.ComposableLayout()`。**但从这一层要单独拆出两个底座件按复用处理**：① `VMActivity` 的 Surface 生命周期管理（`SurfaceView` 创建/销毁与 EGL context 绑定的时序）；② 崩溃重启（ProcessPhoenix 式进程自重启）。这两件如果混进 UI 自写，写游戏 Activity 时必漏崩溃恢复。
- 文件管理：`filemanager/`(含独立 `:filemanager` 进程) 的界面与交互。
- 下载体系：`game/download/` 里的版本、整合包、资源下载界面与源管理——Vaelin 要做源可插拔（第 38 条）与地区闸（第 8 条）。**其中 `download/jvm_server/` 的安装器 JVM 调度按复用处理**（见 §3.3）。
- 联机：`terracotta/` 的 UI；底层 P2P 走 EasyTier（LGPL）自建，理由见 `01-文档/02` §6.3。
- 账号体系：ZL2 的登录流程不复用（规格书无此条目，且第 33 条正版上传是否保留仍待裁决）。

### 3.5 `Launcher.kt` 的依赖锚点

`Launcher.kt`(531 行) 本身没有 Compose import，划入复用正确，但它强依赖一批全局单例，搬它时必须一并就位，否则 T1 编译期大面积报错：`GlobalContext`、`AllSettings`、`PathManager`、`LibPath`，以及 `RendererPluginManager` / `NativePluginManager` / `DriverPluginManager` 三个插件管理器。T1.1 要把这份清单写进 `01-文档/05`。

### 3.6 精确边界怎么定

上面是初判，**逐文件判定是第 1 轮 T1.1 的交付物**，产出 `01-文档/05-启动基底复用清单.md`，每个文件标「复用 / 自写 / 参考」并写一句理由，不靠目录猜。

## 4. 轮次总览

分 8 轮。每轮的准入门槛是前一轮验收通过，避免在错误地基上继续堆。

| 轮次 | 主题 | 出口标志 | 预估任务数（1–2h） |
|---|---|---|---|
| **R1** | 启动底座落地 | 真机装上 APK，能启动一个原版 MC 1.20.1 并进入主菜单 | 15 |
| **R2** | 账号体系（v1.3 新增） | 离线账号能进服务器；微软 device code 登录拿到正版皮肤；第三方外置登录能进对应服务器 | 10 |
| **R3** | 模块系统骨架 | 第三方模块能被导入、加载、显示自有页面、被安全模式短路 | 16 |
| **R4** | 世界工具三件套 | 种子地图能出瓦片图；投影能渲染 .litematic；存档能删区块 | 18 |
| **R5** | 内置功能与主题 | 渐变文字/配方/皮肤/玻璃 UI 四件可用 | 12 |
| **R6** | 联机与 AI 工坊 | 地区闸内正确隐藏；非大陆可 P2P 联机；AI 能生成并装上一个模块 | 14 |
| **R7** | 开发者选项与安全模式 | 13 分区全在 Beta 可见；static shortcut 安全模式生效 | 12 |
| **R8** | 发布准备 | Release 包零开发者入口、文档齐全、真机验收清单交付 | 8 |

**总计约 105 个任务。** 这是估算不是承诺，R4 之后按实际校准。

R1 与 R2 是地基，**逐级放行，R1 不通过不进 R2**。R2 排在模块系统之前，因为账号是"能不能真正玩起来"的前提，且它不依赖模块系统；R1 里只需一个最小离线账号占位（`--username` / `--uuid` / `--accessToken` 传固定值即可进主菜单），完整三类账号在 R2 做。R4 三个工具彼此独立，可并行。R5–R7 可穿插。

1. **ndk-build 在含空格路径下必然失败。** 根因是 `C:\Android\Sdk\ndk\27.3.13750724\build\core\add-application.mk:85` 用 `$(wildcard $(APP_BUILD_SCRIPT))` 校验路径，而 GNU Make 的 `wildcard` 按空格切分参数，`Vaelin Launcher` 被拆成两个 pattern 必然匹配不到，报 `Your APP_BUILD_SCRIPT points to an unknown file`。已改为 CMake，逐目标映射见 `03-项目工程/startup-core/src/main/jni/CMakeLists.txt`。这不是 NDK 版本问题，23 之后任何版本都一样。

### 5.1 R1 期间必须定下：模块页面跑在哪个进程

这个决定影响 R2 的整个导航层，拖到 R2 再定就是重写。

**结论：模块页面跑主进程。** 理由是跨进程没有 Compose 组合通道——Compose 的组合发生在进程内的 `Recomposer` 里，`@Composable` 无法跨进程传递。走独立 `:module` 进程就只有两条路：子进程自己起一套 Compose 宿主，再把画面通过 `SurfaceControl` 或图片流传回主进程。这意味着主题、动画、导航状态、输入焦点全部要跨进程同步，工作量远超收益。所以这条不是取舍，是另一条基本不可行。

代价是模块崩溃会拖垮启动器主进程。这不是新问题，正是规格书第 15 条 L1–L5 存在的理由，处置方式是：**E5 实验（Compose 重组期异常 + 协程异常双路径隔离）从 R2 提前到 R1 做掉**，先证明 `ModuleErrorBoundary` 这两条路径真能拦住，再往主进程里放第三方代码。

另外，游戏内扩展（`InGamePage` / `InGameHost`）排到 R3 之后，不进 R2 首版：`:game` 进程本身崩溃率就高，模块系统一上线就背它的崩溃率不划算。

## 7. 已定项与已排除的伪问题

许可已定（GPL-3.0）。`minSdk` 已查实为 **26**（`02-参考源码/ZalithLauncher2/ZalithLauncher/build.gradle.kts:134-135`，`targetSdk 34`），与本轮 probe 工程一致。

**关于 MC 版本：这一项不需要拍板，此前把它列成待确认项是我的判断错误。** 启动器支持任意版本，由用户在应用内下载、由每个实例自己记录。渲染器与 MC 版本的关系是运行时按实例判断的——`LauncherElements.kt:304-323` 的实际流程是：

1. `Renderers.setCurrentRenderer(version.getRenderer())` —— 从该实例取它保存的渲染器 id
2. 取该实例的 `minecraftVersion`
3. 设备支持 Vulkan 且渲染器走 Vulkan 后端时，**跳过版本检查**
4. 否则比对 `getMinMCVersion()` / `getMaxMCVersion()`，不在窗口内就拦截并弹 `UnsupportedRenderer`，**提示用户换一个渲染器，不是静默替换**

所以「`GL4ESRenderer` 最高支持 1.21.4」只是那个渲染器的支持窗口，用户装更高版本时换一个渲染器即可，跟项目支持哪些 MC 版本无关。ZL2 的七个内置渲染器本来就是这个设计：`GL4ESRenderer` / `PanfrostRenderer` 到 1.21.4，`NGGL4ESRenderer` / `KopperZinkRenderer` / `FreedrenoRenderer` / `VirGLRenderer` 到 `26.3-snapshot-3`（显示口径 26.2）。

**R1 验收挑一个版本跑通即可**，那只是验收样本，不是产品能力边界。

**没有待用户拍板的项了**，此前列出的三项全部已定：

1. **第 33 条「正版上传」——保留**。用户 m01648 原话「那不然呢肯定做呀。离线账号，正版账号，第三方服务器登录我全都要」，账号体系升为规格书第 60 条，正版上传建立在其上（R2 做完账号，R5 做皮肤编辑器时直接复用）。
