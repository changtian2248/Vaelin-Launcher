# 05 · 启动基底复用清单（R1 / T1.1）

> 依据：规格书 v1.2 第 5 行、第 6 条、第 9 条。
> 复用来源：`02-参考源码/ZalithLauncher2`，HEAD `67c63a9ee8`，GPL-3.0。
> 本文逐目录判定 ZL2 的 871 个 Java/Kotlin 文件与 `jni/` 全部 C/C++ 文件中，哪些进入 Vaelin 的 `startup-core`，哪些只读参考，哪些不碰。
> 判定以「把 JVM 拉起来并渲染出画面」为唯一分界线，越过这条线的 UI、下载、账号、模组管理一律自写。

## §0 判定口径

| 档位 | 含义 | 落地动作 |
| --- | --- | --- |
| **直接复用** | 源码复制进 `startup-core`，改包名 `com.movtery.zalithlauncher.* → com.vaelin.startup.*`，保留原文件头的 GPL-3.0 版权声明与作者信息 | 复制 + 改包名 + 跑通编译 |
| **移植改写** | 逻辑照搬，但要去掉对 ZL2 特有单例/设置/UI 的依赖，或换掉存储与路径模型 | 重写依赖注入点后复制主体 |
| **仅参考** | 读实现思路，Vaelin 自己写 | 不复制代码，只在实现文档留指针 |
| **不复用** | 与启动基底无关，或属于 Vaelin 要自建的能力 | 不引入 |

一条硬规则：**被复用文件不得引用「不复用区」的任何类型**。§7 给出已知会违反这条的四类依赖，落地时必须先断开。

### 2.3 构建系统差异（T1.2 已完成，结论与当初的预判相反）

ZL2 用 **ndk-build**（`Android.mk` + `Application.mk`），不是 CMake。当初的判断是「照搬 ndk-build 改动最小」，**实测证伪**：

```
[CXX1429] error when building with ndkBuild using ...\src\main\jni\Android.mk:
Android NDK: Your APP_BUILD_SCRIPT points to an unknown file:
C:\Users\Administrator\Desktop\Vaelin Launcher\03-项目工程\startup-core\src\main\jni\Android.mk
```

根因在 `C:\Android\Sdk\ndk\27.3.13750724\build\core\add-application.mk:83-90`：

```make
APP_BUILD_SCRIPT := $(strip $(APP_BUILD_SCRIPT))
_build_script := $(strip $(wildcard $(APP_BUILD_SCRIPT)))
ifndef _build_script
    $(call __ndk_error,Your APP_BUILD_SCRIPT points to an unknown file: $(APP_BUILD_SCRIPT))
```

`$(wildcard)` 在 GNU Make 里按空白切分参数，工作区路径 `Vaelin Launcher` 含空格，整条路径被拆成两个 pattern，必然匹配不到。**这与 NDK 版本无关**，ZL2 的用户把工程放在含空格目录下同样踩。

- ~~方案 A（推荐）：照搬 ndk-build~~ —— **在含空格路径下不可用，已否决。**
- **方案 B（实际采用）**：手写 `CMakeLists.txt` 等价转写。12 个 `add_library(SHARED)` 与 `Android.mk` 的 `LOCAL_MODULE` 一一对应，`$(call import-module,prefab/bytehook)` 换成 `find_package(bytehook REQUIRED CONFIG)` + `bytehook::bytehook`，`-rdynamic` → `-rdynamic` link option，`-z global` → `-Wl,-z,global`。

**结论：选方案 B（CMake）。** 落地文件 `03-项目工程/startup-core/src/main/jni/CMakeLists.txt`，完成后 `:startup-core:assembleDebug` 通过，12 个 `.so` 全部 `ELF64`/`AArch64`。

转写时发现 `Android.mk` 本身有一个 bug：`:53-55` 的 arm64 `-DADRENO_POSSIBLE` 块落在 `:51 include $(BUILD_SHARED_LIBRARY)` 之后、`:58 $(CLEAR_VARS)` 之前，会被 `CLEAR_VARS` 清空，对任何模块都不生效，是死代码。CMake 版按实际行为处理——`vulkan_check` 不带 `ADRENO_POSSIBLE`。

另有两处 CI 层面的差异必须处理：`Android.mk:113-114` 的 `$(info $(shell (rm ...)))` 是 Unix 命令，Windows 主机上会失败（已注释，改由 Gradle `packaging.jniLibs.excludes` 排除 `libawt_headless.so`）；`awt_headless` 是零源空壳模块，CMake 不接受零源目标，直接不建。

### 2.4 三个构建前置条件（T1.2 的实测结果）

1. **`com.bytedance:bytehook:1.0.10`**：`Android.mk:11` 有 `$(call import-module,prefab/bytehook)`，需要 `buildFeatures { prefab = true }` + `implementation("com.bytedance:bytehook:1.0.10")`。**实测补充**：`pickFirsts += listOf("**/libbytehook.so")` 必须加在 **app 模块**，不是 library 模块——冲突发生在 `:app:mergeDebugNativeLibs`（一处来自 startup-core 的 prefab 复制，一处来自 AAR），写在 library 侧不生效。
2. **NDK 版本**：ZL2 锁 `ndkVersion = "25.2.9519653"`，本机是 `27.3.13750724`。**实测结论：NDK 27 能编过这套 C 代码**，只需改一处——`awt_bridge.c:120` 把 `ReleaseIntArrayElements` 的第 4 参 `NULL` 改成 `0`（clang 18 默认 `-Wint-conversion` 报错，clang 14 只警告）。不需要降级装 NDK 25。
3. **`packaging.jniLibs.useLegacyPackaging = true`**：照搬，`.so` 不压缩存放，`dlopen` 私有目录副本时行为一致。

## §7 依赖闭包风险（落地前必须断开）

被复用文件里已知引用了不复用区的四类：

1. **`Launcher.kt` → `AllSettings` / `PathManager` / `LibPath` / 三个 PluginManager**
   `setting/` 是仅参考区、`game/plugin/` 是不复用区。T1.4 必须先落 `StartupContext` + 三个最小接口（`PathProvider` / `SettingsProvider` / `PluginHook` 空实现），否则 `Launcher.kt` 编不过。
2. **`GameHandler.kt` → `GameScreen`（Compose）**
   拆两半即可，见 §3.1。
3. **`GameLaunchFlow.kt` / `GameService.kt` → `viewmodel/` 与 `notification/`**
   `notification/` 走移植改写（§4.5），`viewmodel/` 全部断开换成回调。
4. **`game/download/jvm_server/` → `GameInstaller.kt`（在 `game/download/game/`）**
   安装器整体属于 §4.3 移植区，`JvmService` 的调用方要跟着改。

另有一条**结构性风险**：ZL2 的 `Renderers` 注册表在 `init()` 里注册七个内置渲染器，`setCurrentRenderer` 找不到时静默回退首个内置。Vaelin 若沿用这个语义，用户选了 `vulkan_zink` 而设备上没有 `libOSMesa.so` 时会静默变成 GL4ES——**这是隐藏的功能失效**。T1.8 起改为：找不到即抛错 + 上层提示换渲染器。

## §10 来源：ZL2 源码深度调研报告的补充发现（2026-11-05）

报告归档在 `05-审查记录/调研/ZL2-源码深度调研.md`（70,511 B / 633 行，第三方对本仓库 HEAD `67c63a9ee8` 的静态分析）。以下只记**改变本清单判断**的条目，其余不重复。

### 10.1 targetSdk 必须停在 34（已落到工程）

`02-参考源码/ZalithLauncher2/ZalithLauncher/src/main/java/com/movtery/zalithlauncher/ui/base/FullScreenAppCompatActivity.kt:143` 原文注释：

> 注：targetSdk 需要设置为 34，从 35 开始，Activity 会被强行加入 enableEdgeToEdge，该实现就会彻底失效

我们复用它的全屏实现（沉浸式 + cutout + `dispatchTouchEvent` 的 raw/局部坐标修正），所以这条约束继承下来。
`03-项目工程/app/build.gradle.kts` 已从 `targetSdk = 36` 改为 `34`，并重新构建验证：`targetSdkVersion:'34'` / `compileSdkVersion='37'` 可共存，APK 62,517,355 字节。

### 10.2 插件体系实际有 5 类，不止渲染器

`02-参考源码/ZalithLauncher2/ZalithLauncher/src/main/java/com/movtery/zalithlauncher/game/plugin/`（18 文件）：

| Manager | 职责 | 文件大小 |
|---|---|---|
| `driver/DriverPluginManager.kt` | 驱动包 | 3,568 B |
| `renderer/RendererPluginManager.kt` | 旧渲染器协议 | 6,771 B |
| `renderer_v2/RendererV2PluginManager.kt` | 新渲染器协议 + 配置 DSL | 4,597 B |
| `natives/NativePluginManager.kt` | native 库包 | 5,675 B |
| `ffmpeg/FFmpegPluginManager.kt` | FFmpeg 可执行包 | 2,940 B |

统一入口 `PluginLoader.loadAllPlugins()`（4,290 B）用 `packageManager.queryIntentActivities(ACTION_MAIN, GET_META_DATA or GET_SHARED_LIBRARY_FILES)` 扫描已安装 APK，插件 `.so` 取自其 `ApplicationInfo.nativeLibraryDir`。
→ **本清单 §3.2 只把渲染器协议划进复用区；其余 4 类是否需要，等用户裁决（已写进规格书第 9 条 v1.4 补记）。**

### 10.3 `BuildKeys` 是编译期生成类，源码里没有

ZL2 根 `build.gradle.kts` 从 **JitPack** 取 `com.github.MovTery.BuildKeys:core:1.0.0`，由 `buildKeys { ... }` 生成 7 个常量：`OAUTH_CLIENT_ID`、`LAUNCHER_NAME`、`LAUNCHER_IDENTIFIER`、`LAUNCHER_SHORT_NAME`、`URL_HOME`、`CURSEFORGE_API`、`BUILD_ARCH`。

复用区里引用它的文件：`bridge/ZLNativeInvoker.kt`（`BuildKeys.LAUNCHER_IDENTIFIER`）、`game/account/*`（OAuth）、`game/addons/mirror/BMCLAPI.kt`（CurseForge key）。
→ **处置**：Vaelin 自建一个 `com.vaelin.startup.BuildKeys`（普通 Kotlin object，值写在 `gradle.properties` 经 `buildConfigField` 注入），不引 JitPack 插件。T1.4 移植 `ZLNativeInvoker` 前必须先把这个类建出来。

### 10.4 `manifest.json` 是构建期生成的，且校验要求文件集合完全相等

ZL2 `build.gradle.kts:58-106` `writeComponentAssetManifests()` 在 `merge<Variant>Assets` 的 `doLast` 生成，源码树里**不存在**这些 `manifest.json`。
`components/AssetManifest.kt` 的 `verifyComponentDirectory()` 逐个比对 size + SHA-1，**且要求文件集合完全相等——多余文件也算失败**。

→ 我们从 Release APK 提取 `components/*/manifest.json` 的路径是对的（APK 里已生成好），但**提取时必须按 manifest 列出的 files 全量核对**，多一个少一个都会让 `checkState()` 一直返回 PENDING。T1.5 之前必须做一次集合比对。

### 10.5 `dlopenJavaRuntime()` 是 10 个库 + 递归全目录，不是 7 个

`game/launch/Launcher.kt:131-201`：先 dlopen `libjli`、`libjvm`、`libfreetype`、`libverify`、`libjava`、`libnet`、`libnio`、`libawt`、`libawt_headless`、`libfontmanager`，**再递归 dlopen 运行时目录下所有 `.so`**；随后 `dlopenEngine()` 加载 `libopenal.so` + 渲染器插件/渲染器库。
→ 本清单 §3.1 里副审之前列的"JRE 7 库清单"要按这个更正。

### 10.6 `setLdLibraryPath` 的拼接顺序是有序契约

`Launcher.kt:131-201` 第 2 步拼接顺序：FFmpeg 插件 → 渲染器插件 → NativeLib 插件 → JRE `lib/jli` → `lib/server` → `/system/lib64` → `/vendor/lib64` → `/system_ext/lib64` → JNA → `runtime_mod` → per-version LWJGL natives → 应用 `nativeLibraryDir`。
→ 复用 `Launcher.kt` 时这一段不能重排，顺序影响符号解析优先级。

### 10.7 多进程下 `onCreate` 会执行 4 次

进程拓扑：主进程（Application + Splash/Main/Error/ControlEditor）、`:game`（VMActivity + GameService + TerracottaVPNService）、`:jvm`（JvmService）、`:filemanager`（FileManagerActivity + EventService）。`ZLApplication` 是 application 级，**每个进程各跑一遍 `onCreate`**，即 MMKV / Fishnet / PathManager / 异常钩子 / TaskKeepAlive 初始化 4 次。
→ 我们的 `VPaths.init()` / `VLog.initialize()` 必须按进程幂等，且日志文件按进程分（现在已经这么做）。另外 `MMKV ID = BuildKeys.LAUNCHER_IDENTIFIER`，改 `launcher_name` 等于所有设置"丢失"——我们不用 MMKV，但**任何持久化键都不要绑死在应用名上**。

### 10.8 退出靠杀进程，不是 finish()

`ZLNativeInvoker.jvmExit(code, isSignal)` → `staticLauncher?.exit()` → `onExit` → `killProgress()` = `Process.killProcess(myPid())`；退出码 0 时 `ProcessPhoenix.triggerRebirth()` 重启启动器，非 0 时进 `ErrorActivity`。
→ 任何依赖 `onDestroy`/`finally` 落盘的逻辑都可能被截断，**要持久化的状态必须在触发退出前写完**。

### 10.9 `progressFinalUserArgs()` 会强制清除一批用户 JVM 参数

`Launcher.kt:324-362` 清除 `-Xms`/`-Xmx`/`-d32`/`-d64`/`-Xint`/`-XX:+Use*LargePages`/`-Dorg.lwjgl.opengl.libname`/`-Dorg.lwjgl.freetype.libname`/`-XX:ActiveProcessorCount`，再统一注入内存、openal/freetype/spvc/allocator 与 CPU 核数。
→ 这是"用户自定义 JVM 参数不生效"类问题的根因，R4 做设置界面时要显式告知用户。

### 10.10 GPLv3 §7 附加条款与规格书第 10 条互相吻合

ZL2 `README.md:47-58`：修改版分发须改名或改版本号、名称中不得含 "ZalithLauncher"/"ZL"、不得用近似名称、必须在启动页或主界面明显标注"非官方修改版"、不得移除版权声明。
→ **Vaelin 这个名字本身就满足前三条**，规格书第 10 条本来就要求标注「非官方修改版」，两者对齐，无额外成本。但"不得移除版权声明"意味着被复用的每个文件都要保留 GPL 头（我们已经这么做）。
