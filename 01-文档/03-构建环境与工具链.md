### 3.1 这套组合已实测跑通（assembleDebug 成功）

用最小 Compose 工程 `06-构建工具/build-check/gradle-probe/` 实跑，**BUILD SUCCESSFUL in 56s / 36 tasks / APK 11,514,152 字节**。过程中踩到并确认了两条会直接卡死构建的坑：

**坑 1：AGP 9.0+ 内置 Kotlin，禁止再 apply `org.jetbrains.kotlin.android`。**
第一次构建的失败原文：

```
* What went wrong:
An exception occurred applying plugin request [id: 'org.jetbrains.kotlin.android']
> Failed to apply plugin 'org.jetbrains.kotlin.android'
  The 'org.jetbrains.kotlin.android' plugin is no longer required for Kotlin support since AGP 9.0.
  Solution: Remove the 'org.jetbrains.kotlin.android' plugin from this project's build file: app\build.gradle.kts.
  See https://kotl.in/gradle/agp-built-in-kotlin
```

推论：调研报告里"KGP 2.4.21 官方兼容表上限是 AGP 9.3.1 / Gradle 9.7.0"这条张力**不适用于 AGP 9.5**——那是按旧插件模型推理出的伪冲突，已被实测证伪。正确写法是只保留 `id("org.jetbrains.kotlin.plugin.compose") version "2.4.21"`（Compose 编译器插件仍然独立于 AGP 内置的 Kotlin 支持之外，必须显式声明）。

**坑 2：Compose BOM 2026.09.00 要求 compileSdk ≥ 37。**
compileSdk=36 时 AGP 直接拒绝构建，原文（节选）：

```
Dependency 'androidx.compose.ui:ui-android:1.12.1' requires libraries and applications that
depend on it to compile against version 37 or later of the Android APIs.
:app is currently compiled against android-36.
```

所以 compileSdk 必须提到 37。`platforms;android-37.2` 安装后的目录名是 `android-37.2`，但 Gradle 侧写 `compileSdk = 37` 能正确命中，不需要写 minor 号。

**targetSdk 保持 36**：compileSdk 可以单独上抬（只是允许用新 API），targetSdk 决定运行时行为，与首版 arm64 的保守取向一致。若后续要跟进 Android 17 的行为变化再单独抬。

**坑 3（2026-11-05）：AGP 拒绝含非 ASCII 字符的工程路径。**
工作区目录改成中文编号（`03-项目工程`）后，AGP 在配置阶段直接中止：

```

> Failed to apply plugin 'com.android.internal.application'.
   > Your project path contains non-ASCII characters. This will most likely cause the build to fail on Windows.
     Please move your project to a different directory. See http://b.android.com/95744 for details.
     This warning can be disabled by adding the line 'android.overridePathCheck=true' to gradle.properties file in the project directory.
```

这个检查本身是启发式警告。关掉之后（`03-项目工程/gradle.properties` 里加 `android.overridePathCheck=true`）**已实测全链路可用**：

## 5. 交叉编译验证（已实际跑通）

这是验收标准第 4 条「构建链能跑通一次构建前检查」的硬证据。

### 5.1 验证内容

用 NDK 把 `02-参考源码/cubiomes` 的 8 个 .c 文件编成 `arm64-v8a` 静态库，再链接一个最小 JNI 桩导出为 `.so`，全流程在**真实工作区路径**（`C:\Users\Administrator\Desktop\Vaelin Launcher`，含空格）下完成。

### 5.2 文件

- `tools\build-check\CMakeLists.txt`
- `tools\build-check\jni_stub.c`

`CMakeLists.txt` 的要点：
- `add_library(cubiomes STATIC ...)` 直接列 cubiomes 的源文件，**不 include 它自带的 CMakeLists**（那份会额外产出 SHARED 目标，且 `cmake_minimum_required(VERSION 2.8)` 已被 CMake 弃用）。
- `add_library(vaelin_cubiomes SHARED jni_stub.c)` 链接 cubiomes + `log` + `m`。
- 引擎 ABI 常量 `VAELIN_CUBIOMES_ABI = 1ULL` **单点定义在 C 侧**，Java/Kotlin 侧只经 JNI 读取。禁止四处各自硬编码——这是 Axolotl 踩过的坑（C 侧、Rust 侧、前端 `backend.ts`、版本映射表四处同步引擎 revision）。

### 5.3 可复现命令

```powershell

$env:ANDROID_NDK  = "C:\Android\Sdk\ndk\27.3.13750724"
$cmake = "C:\Android\Sdk\cmake\3.31.6\bin\cmake.exe"
$ninja = "C:\Android\Sdk\cmake\3.31.6\bin\ninja.exe"
$src   = "C:\Users\Administrator\Desktop\Vaelin Launcher\06-构建工具\build-check"

& $cmake -S $src -B "$src\build-arm64" -G Ninja `
  "-DCMAKE_TOOLCHAIN_FILE=$env:ANDROID_NDK\build\cmake\android.toolchain.cmake" `
  "-DCMAKE_MAKE_PROGRAM=$ninja" `
  -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-24 -DCMAKE_BUILD_TYPE=Release
& $cmake --build "$src\build-arm64"
```

### 5.4 结果

- configure exit **0**，build exit **0**，11 个编译/链接步骤全部通过。
- 唯一输出是 NDK 的 `flags.cmake:18 (cmake_minimum_required)` 弃用警告——来自 NDK 自身，无害。

**关于 `-DANDROID_PLATFORM=android-24` 与 minSdk 26 的差异（副审提出的点，说明如下，不改）**：
`ANDROID_PLATFORM` 控制的是**native 侧链接的 NDK API 级别**，与 Java 侧的 `minSdk` 是两个独立维度。native 用 24（低于 minSdk 26）是保守选择：它保证编译出来的 .so 只引用 API 24 就已存在的 libc/libm 符号，在任何 minSdk ≥ 26 的设备上必然可用。反过来把 native 抬到 26 只是放宽了可用符号范围，没有任何收益，还会缩小将来降 minSdk 的余地。**所以这里保持 24 是对的，不是笔误。** 真正的工程要求是：`CMakeLists.txt` 里显式写死这个值，不要让它随 Gradle 的 `minSdk` 自动推导。

### 6.0 Nucleation 的实际结构（这决定了第 35 条的做法）

它不是一个只做 meshing 的小库，而是**一整套体素/schematic 工具链**。`src/` 下 25 个子目录，与第 35 条直接相关的有：
- `formats/`（schematic 各格式读写，含 `nbt/` 相关）
- `meshing/`（greedy meshing —— 我们真正需要的那块）
- `bridge/`（跨语言绑定层，官方多语言绑定由它单源生成）
- `region_storage/`（region 文件存储，第 36 条存档编辑器可参考）
- `schematic_builder/`、`selection/`、`simulation/`、`voxelize/`、`blockpedia/`

**三个必须提前知道的限制**：
1. **crate 包内没有 `examples/ffi.md`**，也没有任何文件名含 ffi 的文件。之前调研说的 FFI 说明在 GitHub 仓库里，crates.io 分发的 crate 包不含 `examples/` 的完整内容。要用得按 `src/bridge/` 自己推。
2. **官方无 Android 构建先例**。JVM 绑定的 natives 只列 linux x64/arm64 与 macOS。要上 Android 必须 `rustup target add aarch64-linux-android` + `cargo-ndk` 自建，本机 Rust 工具链未装未验证。
3. 它自带 `build.rs`，构建时会跑构建脚本——交叉编译时这点要单独处理。

**备选路径**：如果 Rust 链迟迟不通，第 35 条可以先用纯 Kotlin 实现 greedy meshing（算法本身不复杂），把 Nucleation 降级为格式兼容性参考。这不违反规格书，但会改变第 35 条的工期。

### 6.1 schematic4j 的额外价值

它自带 `net.sandrohc.schematic4j.nbt` 包：`NBTInputStream` / `NBTOutputStream` / `LittleEndianNBTInputStream` / `NBTSerializer` / `MaxDepthIO` 等，是一套完整的 Java NBT 读写实现。第 36 条存档编辑器需要的 NBT 层可以直接复用它，不必另找库——这同时消除了"存档编辑器用哪个 NBT 库"这个不确定项。

### 6.2 下载通道说明（这是本轮最费时的一块，写清楚免得重踩）

`github.com` 在本机 443 超时、`api.github.com` 403、`codeload.github.com` 超时，**全部直连不可用**。实测结论：

| 通道 | 可用性 | 适用场景 |
|---|---|---|
| **blobless 稀疏克隆**（`--filter=blob:none --no-checkout` + `sparse-checkout`） | **可用，1–2 秒拿到完整文件树** | **大仓库的唯一可行通道，9 个仓库最终都走这条** |
| `gh-proxy.com` + `archive/refs/heads/<branch>.zip` | 小/中仓库可用 | 小仓库（< 15 MB） |
| 同上，大仓库 | **服务端打包阶段卡成 0 字节，永不返回** | 不可用 |
| `gh-proxy.com` + `git clone --depth 1`（全量） | 可用但慢（skinview3d 82 s） | 中等仓库 |
| `gh-proxy.com` + `raw.githubusercontent.com/<path>` | 可用 | 单文件精确取 |
| **`static.crates.io/crates/<name>/<name>-<ver>.crate`** | **直连可用，1.97 MB / 0.62 s** | Rust crate，比代理快两个数量级 |
| `gitee.com/api/v5` | 200 | 备选 |
| `ghproxy.net` / `ghfast.top` / `gh.llkk.cc` / `kkgithub.com` / `bgithub.xyz` / `mirror.ghproxy.com` / `ghproxy.cc` | 全部失败 | 不可用 |

**关键教训（花了近一小时才摸出来，值得记住）**：
1. 不要对一个下载失败就换镜像试；先看失败形态。**0 字节且长时间不返回 = 上游打包卡死**，换同类型的镜像一样会卡；这时应该换**通道类型**（archive → blobless clone → raw 单文件 → 源站直连），而不是换镜像域名。
2. `--filter=blob:none --no-checkout` 的克隆**只下 commit 和 tree，不下文件内容**，所以 1–2 秒就完成，再用 `git ls-tree -r --name-only HEAD` 拿到全量文件清单——这一步就能定位关键文件路径，再按需 checkout。比盲目猜 raw 路径快得多（之前猜 Pojav 的 `utils/LauncherProfiles.java` 猜错，实际在 `value/launcherprofiles/LauncherProfiles.java`）。
3. sparse-checkout 一定要排除运行时分发物（JRE 的 `tar.xz`、博客的 `mp4`），否则 modrinth-code 一个仓库就 238 MB。
